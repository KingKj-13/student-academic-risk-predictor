# Code guide and viva preparation

Read this with the code open. You should be able to explain every answer below in your own words.

## What happens when "Predict risk" is clicked

1. `static/js/predict.js` collects the form and sends JSON to `POST /api/predict`.
2. `schemas.StudentIn` checks types and ranges. Bad input returns status 422 and nothing is stored.
3. `predictor.RiskPredictor` runs the saved pipeline: fill missing values, scale numbers, encode the
   Yes/No field, then Logistic Regression gives a probability for Low, Medium and High.
4. The same class works out contributing factors by changing one input at a time.
5. `db.Database.save_predictions` updates the student and adds a history row in one transaction.
6. `alerts` decides the status and suggestions, and raises an alert if the student has newly become High.
7. The browser draws the result using `textContent`, so a name containing HTML is shown as plain text.

## What happens during training (`train.py`)

1. **Clean:** unify spellings, turn impossible values into missing values, remove duplicates.
2. **Explore:** save graphs.
3. **Split:** 80% training, 20% test, stratified so both keep the same class mix.
4. **Pipeline:** imputation, scaling and encoding are learnt from training data only.
5. **Search:** 5-fold cross-validation over a few settings for each of three models.
6. **Select:** score = 0.5 x High-risk recall + 0.5 x macro F1, using cross-validation only.
7. **Test once:** report accuracy, precision, recall, F1, confusion matrix.
8. **Save:** the whole pipeline goes into one file, so the app preprocesses exactly as training did.

## Likely questions

**Is this real student data?**
No. It is synthetic, generated by `generate_data.py`. The label is a noisy weighted score of the inputs, so
the results show the method works on that rule. They do not prove it works on real students.

**Why did Logistic Regression beat Random Forest?**
The labels were built from a weighted sum, which is close to what a linear model assumes. A more complex
model has no extra pattern to find. On real data the order could change.

**Why not choose by accuracy?**
Missing a High-risk student costs more than a false alarm, and "always say Low" already gets 55% accuracy.

**What is recall for the High class?**
Of the students who really were High risk, the share the model found: 16 of 18 on the test set.

**What is precision?**
Of the students the model called High, the share that really were: 16 of 22.

**What is data leakage and how is it avoided?**
Test information influencing training. Imputation and scaling are inside the pipeline, so they are fitted
on training folds only.

**Why is gender not an input?**
So the model cannot treat two otherwise identical students differently because of it. Gender is still used
to check whether recall differs between groups. Removing a column does not by itself guarantee fairness,
because other columns can carry the same information.

**How are contributing factors found?**
For one input at a time, replace the student's value with the typical Low-risk value and predict again. If
the risk drops by at least 0.05, that input is listed. This describes the model, not the true cause.

**What does the confidence mean?**
The model's probability for the chosen class. The Brier score and expected calibration error measure how far
to trust it. In the middle ranges the test set shows the model is somewhat over-confident.

**Why SQLite?**
It needs no server and suits one department. Many simultaneous writers or several app servers would call
for PostgreSQL.

**How is SQL injection prevented?**
All values are passed as query parameters, never pasted into the SQL text.

**What security does it have, and what is missing?**
Input validation, upload size limits, optional password, same-origin check, security headers. Missing:
individual teacher accounts, roles, audit log, rate limiting.

**What would you do next?**
Get real, consented data; retrain and re-check calibration and fairness; add teacher accounts; track
attendance over time as a feature.
